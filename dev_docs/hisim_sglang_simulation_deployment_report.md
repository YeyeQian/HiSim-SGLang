# HiSim + SGLang 联合仿真环境部署与能力汇报

## 一页式摘要

本项目已在无 GPU 服务器上完成 HiSim 与 SGLang 的 CPU-only Docker 化部署，并跑通“请求生成—SGLang HTTP 接入—请求排队与调度—HiSim 耗时预测—benchmark 汇总与结果校验”全链路。当前环境保留了真实的 SGLang 服务接口和调度流程，但以 HiSim 预测结果替代模型在 GPU 上的实际计算，因而适合用于集成验证、负载建模、调度趋势观察，以及功能兼容性、数据完整性和仿真可执行性的低成本预筛选。

当前固定验证对象为 Qwen3-8B 模型结构和 SGLang `0.5.6.post2`。运行环境采用 Python `3.10.12`、CPU 版 PyTorch `2.9.0+cpu`、HiSim `0.1.0`、AIConfigurator `0.5.0`、Transformers `4.57.1`、XGBoost `2.0.3` 和 NumPy `1.26.4`。容器未加载完整 Qwen3-8B 权重，未执行真实模型 forward，也未初始化 CUDA 或 NCCL。

系统已经形成三类用途明确的 workload：

- `random-ids probe`：2 个短请求，用于快速、离线、确定性的连通性检查。
- `random-ids small`：16 个并发请求，用于观察负载提高后的模拟排队与调度趋势。
- `ShareGPT`：16 个从真实对话数据抽样的请求，用于引入更接近实际业务的文本和长度分布，但不评估回答质量。

现阶段成果应定位为“可复现的联合仿真与集成验证基线”，而不是实体 GPU 性能测试平台。官方 H20 predictor 数据路径已成功接入，但该结果只证明数据和功能路径可用；后续设备扩展应采用面向目标 GPU 的通用数据接入、校准和验证流程，不将总体能力绑定于某一种 GPU。

## 部署成果

1. 已构建固定版本的 CPU-only Docker 运行环境，统一了 SGLang、HiSim、AIConfigurator、CPU PyTorch 和预测依赖，降低宿主机环境差异对复现的影响。
2. 已验证真实 SGLang HTTP 服务、请求队列和调度路径能够在无 GPU 条件下由 HiSim 接管模型执行耗时。
3. 已建立 generic、官方 H20 数据路径和 ShareGPT 三类分级结果标签，明确区分基础链路、设备数据集成和 workload shape，避免把模拟输出误报为真机实测。
4. 已建立结果来源约束和自动校验机制，服务类型、数据集、benchmark profile 与结果类别必须一致，失败请求和关键指标也会受到检查。
5. 已完成宿主机一次性数据准备、容器只读挂载与离线复用设计。基础 `random-ids` 测试不依赖 ShareGPT，可在已有镜像和缓存条件下快速执行。
6. 服务仅绑定本机回环地址，并设置 CPU、内存和共享内存资源上限，便于在共享服务器上以受控方式运行。

以下数字仅为 HiSim 仿真时钟下的代表性输出，不是实体 GPU 测量值，不应直接用于生产 SLA 或容量承诺：

| 场景 | 完成请求 | 模拟吞吐量 | 平均 TTFT | 平均 TPOT |
| --- | ---: | ---: | ---: | ---: |
| generic probe | 2 | 58.89 req/s | 7.34 ms | 6.65 ms |
| H20 数据路径 probe | 2 | 59.37 req/s | 7.33 ms | 6.59 ms |
| H20 数据路径 small | 16 | 30.86 req/s | 288.83 ms | 7.70 ms |
| ShareGPT workload | 16 | 4.18 req/s | 197.78 ms | 6.96 ms |

这些结果可用于确认链路和观察不同负载形态下的模拟趋势。不同 profile 的请求长度与并发条件并不相同，因此不宜仅凭表中数字进行设备横向比较或归因分析。

## 当前能做什么及其优点

当前环境能够支持以下工作：

- 在没有 GPU 的服务器上持续开发和回归 HiSim 与 SGLang 的接口集成，提前发现启动、请求、调度、结果输出和版本兼容问题。
- 使用固定长度的 `random-ids` 或 ShareGPT 真实对话长度分布，观察请求规模、上下文长度和并发变化下的模拟排队与吞吐趋势。
- 验证特定目标设备的 predictor 数据能否被正确组织、加载和驱动仿真，为后续扩展其他 GPU 建立标准接入方式。
- 在申请或占用昂贵 GPU 资源前，预筛功能兼容性、数据完整性和仿真可执行性；完成真机校准闭环后，才进一步用于性能方案预筛选。
- 通过容器、固定版本、离线缓存和规范化结果分类提高复现性，使不同时间的回归结果具有一致的解释边界。

其主要优点是资源门槛低、部署可控、执行快速、适合自动化回归，并能够把“集成是否正确”“负载形态如何变化”和“真机性能是否达标”拆分成不同验证阶段，避免在早期功能开发中反复占用 GPU。未经真机校准的当前结果不应用于淘汰或选择性能方案。

## 当前不能做什么

### MoE 与 DeepSeek-V3

当前不能宣称已经支持或部署 DeepSeek-V3 等 MoE 模型。虽然预测代码包含 `deepseek_v3`、`kimi_k2`、`qwen3_moe` 等模型类型以及 MoE TP/EP 参数入口，但模型类型可被代码识别并不等于已经具备可靠预测能力。要形成可用能力，仍需补充模型结构元数据、算子性能数据、专家路由与通信建模、目标设备数据、配置适配、校准结果和端到端 benchmark。

### TP/EP 并行

当前结果仅覆盖 `tp_size=1` 和 `ep_size=1`。仿真配置虽暴露 TP、EP 参数，但尚未验证大于 1 的配置；现有 H20 数据还缺少部分可选 collective 表。因此，不能据此推断多卡张量并行、专家并行的扩展效率，也不能给出不同 TP/EP 组合的最优结论。

### 多 GPU 与多节点

当前服务器没有执行真实 GPU kernel，也没有初始化 NCCL communicator。系统尚未覆盖多 GPU 通信拓扑、跨节点网络、通信与计算重叠、显存碎片、驱动故障和 kernel 抖动等真实因素。当前也不支持用单卡仿真结果线性外推多卡容量。

### 性能与质量结论

当前模拟指标不能直接回答某一实体 GPU 能承载多少生产用户、是否满足特定 SLA，也不能用于比较不同 GPU 的真实性能。系统不执行真实模型 forward，因此不能评估答案正确性、幻觉或模型质量。上游 HiSim 曾报告特定 H20/Qwen3 场景预测误差低于 5%，该结果表明校准后可能具备较高预测精度，但本项目尚未独立复现，不能将其作为当前环境的精度承诺。

## 四阶段未来路线

### 第一阶段：巩固单模型、单设备仿真基线

完善 Qwen3-8B 的负载矩阵，覆盖更多输入/输出长度、并发度和到达分布；增加 HiCache 专项 profile；将模拟结果与少量可获得的真机数据进行对照，建立误差统计、适用范围和回归阈值。该阶段的目标是把“功能可用”推进到“边界明确、趋势可复核”。

### 第二阶段：模型和目标 GPU 通用化

将当前脚本中的固定模型配置抽象为受控参数，建立模型元数据、算子库、设备数据和 workload profile 的版本化组合。选择一个新增 dense 模型和一种新增目标 GPU 作为样板，完成从数据准备、配置校验到真机对照的完整流程。H20 作为当前已接入实例保留，但总体架构不绑定具体 GPU 型号。

### 第三阶段：MoE 与 TP/EP 并行建模

以 DeepSeek-V3 或另一种代表性 MoE 模型为候选，补充专家路由、计算、通信与负载不均衡数据；完善 collective 性能表，建立 TP/EP 组合测试矩阵。先验证仿真链路和趋势，再使用目标 GPU 真机结果校准，避免仅凭现有代码入口宣称支持。

### 第四阶段：多 GPU、跨节点与决策支持

引入设备拓扑、节点间网络、通信竞争和计算通信重叠模型，验证多 GPU 与跨节点场景。建立仿真结果与实测数据的持续对齐机制，在误差边界稳定后，再逐步用于架构选型、资源预算和容量规划；任何面向生产的结论仍应保留真机压测确认环节。

## 建议下一步

建议优先开展第一阶段校准闭环，而不是立即扩大模型和硬件范围：选定一套可获得真机数据的 Qwen3-8B 单卡场景，统一请求长度、并发度、调度参数和指标定义，对 probe、small、ShareGPT 三类 workload 分别采集仿真与真机结果，形成误差表和适用范围。

在该基线稳定后，再并行推进两项工作：一是将模型和目标 GPU 配置参数化，验证新增 dense 模型与新增设备数据的接入流程；二是为 DeepSeek-V3、TP/EP 和 HiCache 分别建立独立的验收标准。只有在数据完整、端到端测试通过且真机校准达到预设阈值后，才将对应能力标记为“已完成”。
